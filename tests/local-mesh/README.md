# Local N-node mesh

Brings up a complete DKMS deployment — SDN + N×(qkc, orr, dkms) — on a single
machine, from the same `node.yml` files and the same `render_config.py` the
images use ([docker/README.md](../../docker/README.md); the deployment model
in [docs/deployment.md](../../docs/deployment.md)). It exercises the real
deployment contract, not a configuration invented for the test.

It does not replace [`../testbed/`](../testbed/), which runs against the real
deployment over SSH and is where the things that depend on the network are
measured. This is what can be repeated without hardware, in minutes, before
touching the testbed.

```bash
cargo build --release
./mesh.sh up 10            # bring up the mesh
./mesh.sh keys             # ETSI-014 exchange per ordered pair
./mesh.sh down
```

## What it checks

`mesh.sh keys` is the one that matters. For every **ordered** pair of DKMSs:
the master SAE requests `enc_keys` from its DKMS, the slave retrieves that
`key_ID` with `dec_keys` from its own, and the bytes are compared. The
comparison is the point — the session key travels OTP-wrapped with a
transport key and carries no integrity of its own, so a misalignment of the
material would hand the two SAEs different keys without anything failing.
Ordered rather than unordered because one end's `buffer_enc` is the other
end's `buffer_dec`: A→B and B→A spend different material and can fail
separately.

With N=10 that is 90 exchanges; it takes about 15 s.

## Topology

`mesh.sh up N [ring|star|random]`, and the choice changes what is measured:

| | What it builds | What for |
|---|---|---|
| `ring` (default) | ring + chords; with N=10, 14 edges and degrees 2-3. Not the campaign's `ring`, which is the pure cycle C_N (10 edges at N=10) generated by `topologies.py` and run as `custom` | the friendly case: connected, no single point of failure, and alternative paths for the multipath |
| `star` | everyone hanging off node 1; degrees 9 and 1 | loads a single QKC with everything that is not its own. **Removing the hub splits the network**, so node removals must be done on a leaf |
| `random` | seeded connected graph (`DKMS_MESH_SEED`, default 42); with N=10, 15 edges and degrees 2-6 | what resembles a real deployment, where nobody wires a perfect ring |

The random one is built as a random spanning tree plus extra edges up to a
mean degree of ~3: a plain `G(n,p)` can come out disconnected, and a split
mesh does not measure what you want to measure, it measures something else.
A fourth form, `custom`, takes the edge list from
`DKMS_MESH_EDGES="1-2 2-3 …"` (`a-b:km` sets a per-edge distance in `qkd`
mode); the campaign's six families are generated that way by
[`topologies.py`](topologies.py).

In all three, each edge is declared by **one end only**, on purpose: that is
what checks that the SDN passes it on to the other end (see ["Peers ride back
on the announcement"](../../docs/engineering-notes.md#peers-ride-back-on-the-announcement)).

Measured locally with N=10, the 90 ordered pairs give identical bytes in all
three, and the mesh is **full** in about 75 s. Two convergence figures are
used in this document and the campaign: **up** = every module announced and
in the SDN graph (the campaign's "comes up in 6–28 s"), **full** = every
transport buffer at capacity, which is what the figures below measure.

## Simulated QKD links

By default the links are PQC: the QKCs derive the keys between themselves
with ML-KEM. With `DKMS_MESH_LINK_TYPE=qkd` **one `quditto` per edge**
([quditto/README.md](../../quditto/README.md)) is
brought up and the QKCs pull the material from it over ETSI-014.

```bash
DKMS_MESH_LINK_TYPE=qkd ./mesh.sh up 10 ring
```

Two differences that are not details:

- **Both ends declare the link.** The SDN cannot supply the `kme_url` — it
  does not know where that institution's KME is — so a link declared by one
  side only would be left half done. In PQC it is still declared by one end
  only, on purpose.
- **The edge capacity starts to mean something.** In PQC it is whatever the
  operator declares (`capacity_keys_per_s`, 10 000 by default); in QKD the
  SDN sizes it as `cap = R0·10^(−α·d/10)`. With the defaults (`R0=2000`, `α=0.2`, `d=5km`)
  that gives **1588.7 keys/s per edge**, and `mesh.sh up` prints it at
  start-up. Careful: [**the capacity is NOT R0**](../../docs/engineering-notes.md#theoretical-rate--not-r0),
  and confusing the two has cost more than one "deficit versus the
  theoretical" that was not one.

One quditto per link, shared by its two QKCs, so `R0` is per link, not per
direction ([quditto/README.md](../../quditto/README.md#what-it-is-for-and-what-it-is-not)).
Adjust it with `DKMS_MESH_R0`, `DKMS_MESH_ALPHA` and `DKMS_MESH_DIST_KM`.

## Measuring

```bash
./stress.sh --arm A                 # factory defaults
./stress.sh --arm B --tokens 3200   # with the ceiling raised
./bootstrap_times.py                # convergence times of the live mesh
```

`stress.sh` loads **every ordered pair at once** (90 with N=10) and produces
three segments per sweep point: a burst with the buffers full — which
measures the service path, mTLS + OTP + ETSI-020, without the generator in
between —, sustained once the buffer has drained — which measures the
DKMS→ORR→QKC chain — and recovery. The load client is
[`tests/loadgen`](../loadgen/) (`target/release/sae_load`, rustls); it falls
back to [`../testbed/sae_load.py`](../testbed/sae_load.py), same CLI and CSV,
only when the binary is not built (that one needs OpenSSL ≥ 3.5).

**The two arms exist because with the defaults the ceiling is not the
system's, it is ours**: `tick_ms=100` × `max_tokens_per_peer_per_tick=32` is
320 keys/s per peer. Arm A characterises what an operator gets; arm B raises
that ceiling and disables the per-SAE bucket so that the real limit shows.
Measured locally with N=4 and 2 threads per pair: 243.8 keys/s per pair
sustained against the ceiling of 320, with p50 = 2.9 ms and p99 = 9.3 ms.

### QKD vs PQC: the topology only shows when capacity means something

The same three topologies, 10 nodes, with `LINK_TYPE=qkd` (CESGA,
2026-08-24), at 1 thread per pair:

| Topology | PQC | QKD | Fibre ceiling | Reaches it? |
|---|---|---|---|---|
| ring (14 edges) | 7 773 | 7 594 | 11 121 (at 2.0 mean hops) | no — the generator rules |
| random (15) | 7 759 | 7 714 | 11 915 | no — the generator rules |
| **star (9)** | 7 855 | **6 706** | **7 943** | **yes, at 84 %** |

The fibre ceiling comes from `9 edges × 1588.7 keys/s ÷ 1.8 hops per key`
(in the star, 18 of the 90 ordered pairs cross one edge and 72 cross two,
through the hub).

**With PQC the star performed like the ring; with QKD it is 14 % worse at 1
thread and 33 % worse at 4.** The 1e9 sentinel the PQC edges carried until
2026-08-25 ([engineering notes](../../docs/engineering-notes.md#active-known-issues--gotchas),
"PQC edges carry a declared capacity") was hiding
the cost of the topology entirely: without a finite capacity, concentrating
all the traffic on a hub made no difference. Ring and random never touch
their fibre ceiling, so there the bottleneck is still the DKMS emit loop.

And the SDN's signal starts to make sense: **1 100-1 150 keys/s** at the
maximum, versus the ~9·10⁷ it reported in PQC.

### Multipath enabled: before and after (QKD ring, 10 nodes)

Third run of the same recipe (`9245927`), with routing now derived from
topology+capacity instead of the LP's edge flows, and the generator no
longer overshooting the buffer:

| | Shortest path (`9238237`) | Multipath (`9245927`) |
|---|---|---|
| sustained, 1 thread/pair | 13 666 keys/s | **14 752** (+8 %) |
| sustained, 4 and 16 threads | 11 973 / 10 222 | 11 927 / 10 192 (same) |
| **empty ENC buffer** under load | **36 %** of the samples | **1 %** |
| idle links under load | yes (dry next to stalled) | **0** — `taken` within a 1.5× band |
| commodities with `level>capacity` | 90/90 | **0** |
| integrity | 2 600 identical | 2 600 identical |

The honest reading: the aggregate throughput barely rises (+8 % at the
optimum, the same at higher concurrency, where the service path binds)
because the aggregate fibre was already close to its limit. What changes is
**how** it is served: all 28 sampled link ends are working (median `taken`
262 860, minimum 209 814), the buffer almost never empties, and recovery
after the load drops from 26-36 s to 25-30 s. The system goes from "some
edges at the limit and others stalled" to "all the fibre in play" — which is
the property that matters when demand is not uniform.

### The emit loop: before and after (QKD ring, 10 nodes)

Same recipe, `9229899` against `9238237`, changing only that the generator
emits to every peer at once under a global bound instead of one after
another:

| Concurrency | Before | After | |
|---|---|---|---|
| 1 thread/pair | 7 594 keys/s | **13 666** | +80 % |
| 4 threads/pair | 7 477 | **11 973** | +60 % |
| 16 threads/pair | 5 595 | **10 222** | +83 % |

Per ordered pair, from **84.4 to 151.8 keys/s**, against the 139 the SDN
allocated on average: the DKMS goes from consuming 60 % of what it is given
to consuming all of it. The mesh is also full in 57 s instead of 72,
because the buffers fill sooner. Integrity intact at the new rate.

**And the bottleneck moves to the fibre**, which is where it should be in a
QKD system. The QKC keystore under load:

```
peer=8  enc=362  dec=368  misses=0        wenc_to=0
peer=9  enc=311  dec=370  misses=0        wenc_to=0
peer=1  enc=0    dec=63   misses=248974   wenc_to=28
peer=5  enc=0    dec=0    misses=355813   wenc_to=0
```

Note the detail: **it is not evenly spread**. The links to 8 and 9 keep
stock while those to 1 and 5 are dry. That explains why the aggregate
exceeds the ceiling obtained by computing with uniform mean hops (11 504
keys/s at the 1.93 mean hops of this run; the table above uses 2.0): the traffic is not shared equally among the
edges, some saturate and others sit idle. It is a matter of the MCMCF split
and it is the next thread to pull.

### What came out of CESGA (10 nodes, 2026-08-21)

Four campaigns on FT3 compute nodes, ~25 min each:

| Topology | 1 thread/pair | 4 threads/pair | 16 threads/pair |
|---|---|---|---|
| ring | 7 773 keys/s | **8 077** | 5 702 |
| star | 7 855 keys/s | **8 146** | 5 512 |
| random | 7 759 keys/s | **8 059** | 6 048 |

All three behave the same, and the star not being worse is a result: the hub
ends up with degree 9, but the DKMS↔DKMS transport is PQC end to end and does
not lean on the graph. The optimum is at 4 threads per pair; at 16 the rate
**drops** and the p50 latency goes from 7.5 to 39 ms — oversaturation, not
breakage: it keeps serving with integrity intact.

7 800 keys sampled with `dec_keys` under load, all with identical bytes.
`recv_corrupt = 0` in all three meshes and the 30 ORRs with
`dropped_no_secret = 0` and `peel_failed = 0`. The mesh is full in 70 s.

**Arm B showed that the default ceiling is what keeps the system stable.**
At 1 thread per pair it gave 21 714 keys/s aggregate (241 per pair) and
**zero rejections**, almost three times as much. But at 4 threads it
collapsed to 2 749, at 16 it was left at 32 and the job died of OOM at
16.6 GB, against the ~6 GB arm A holds steady at. Without that cap the
generator produces faster than the ORR→QKC chain transports and the queues
grow unchecked: **there is no back-pressure between the generator and the
transport**, and the cap was standing in for it.

The report attributes the rejections on its own, which is what avoids
drawing false conclusions: a `429` with the ENC buffer empty is legitimate
back-pressure — demand exceeds the refill —, not a capacity limit. That is
why the sampling also collects the rate the SDN assigns, which in a PQC-only
deployment meant nothing at the time and could drop to zero (see the
sentinel above).

And it samples integrity under load: it retrieves with `dec_keys` a sample of
the served keys and compares the sha256. A single mismatch would matter more
than the whole throughput curve.

`bootstrap_times.py` instruments nothing: it relies on each module's periodic
log lines and on `starts.tsv`, which `mesh.sh` writes with the exact instant
it launches each process — t0 is the launch and not the first log line,
because between the two lies initialisation, which is part of what is being
measured.

## Changing the topology live

`mesh.sh link <n> [neighbours...]` rewrites the neighbours a QKC declares and
restarts it (what the SDN does with that:
[auto-configuration.md § Rewiring a link](../../docs/auto-configuration.md#rewiring-a-link)). That creates, modifies and removes links, because the
announcement is authoritative over what that QKC declares: no longer naming a
neighbour retires the edge if the other end does not declare it either.

```bash
./mesh.sh link 2 3 7       # qkc2 now has fibre to 3 and 7
./mesh.sh link 2 3         # ...and drops the one to 7
./mesh.sh edges            # edges + connectivity check
```

To retire a whole node, kill its three processes and wait for
`presence_ttl_secs` (90 s by default): the SDN drops it along with its edges
and the rest find out on their own.

## Memory

Everything runs inside a systemd scope with `MemoryMax=8G`
(`DKMS_MESH_MEM_MAX` to change it). Where the scope cannot be created — inside
a SLURM job there is no user session bus — it starts without one and warns:
there the cap is the job's `--mem`, which is a cgroup just as real. Outside
SLURM and without a scope there is no cap at all, and the script says so.

The cap matters: a local deployment has eaten a desktop session before — see
the [saturation section of `docs/engineering-notes.md`](../../docs/engineering-notes.md#saturation--load-tests--run-isolated).
With N=10 the measured peak is 0.46 GB (PQC links, idle after the fill;
the campaign's N=10 cells with QKD links under load reach 7.0 GB), so the
8 GB are margin, not a constraint.

## Where it leaves things

In `tests/results/local-mesh/` (gitignored): rendered configs, certificates
and logs of the 31 processes. `mesh.sh up` wipes and recreates it, so do not
keep anything there that you want to preserve.

The certificates are issued by [`docker/gen-certs.sh`](../../docker/gen-certs.sh)
with a single CA for the whole mesh, which is what the mTLS between DKMSs
requires. SAE client certs carry the identity in the SAN
(`URI:urn:dkms:sae:<id>`), which is where the DKMS reads it from.

## Known limits

- **N between 2 and 100.** Node `n` takes the ports `20000 + 100·(n−1)`
  to `+9` (29 909 at N = 100) and the quditto of edge `i` listens on
  `30000 + i`, so 100 is where the ranges run out. The 2026-09 campaign ran
  the six families at N = 10 to 100 on this harness
  ([campaign 2026-09](../../docs/results/campaign-2026-09.md)).
- **Everything is simulated.** The `qkd` mode runs one quditto per edge on
  loopback, in plaintext (`QUDITTO_TLS=off`, the only plaintext element
  besides the SDN's read-only mirror): no hardware and no per-KME PKI.
- **Single host.** It measures nothing about latency or the network.
