# Memoria del agente multipath-sdn

Fecha de inicio: 2026-05-18

## Contexto inicial (sembrado por el usuario al scaffolding)

### Sobre el solver actual

- `sdn/src/mcf.rs` YA tiene K-shortest paths implementado (Yen's), pero
  descarta paths 2 y 3 — solo usa `paths.first()` (líneas
  aproximadas 375, 441, 537; verificar exacto en la primera iteración).
- `McfSnapshot.forwarding[i]` ya está estructurada con un campo
  `omega: f64` (ratio). Hoy siempre vale 1.0; el cambio es emitir
  múltiples entries con ratios.
- El solver mantiene dos tiers HIGH={Priority, Important, Quickly}
  y LOW={Relax, BestEffort}. Pesos QoS decade-spaced 10000/1000/100/10/1.
  Saturated = rate 0 (excluido del LP).

### Sobre el cliente del routing

- ORR ya hace **source routing** via `app_header["orr_path"]`. No hay
  que cambiar el wire format. Solo cambia lo que el ORR mete ahí: en
  vez de "siempre el path P0", ahora muestrea P0/P1/P2 con ratios
  omega.
- QKC es **destination-based** (`dest_id → next_hop`). NO es per-flow
  ni per-path. No hay que tocarlo.

### Sobre EKS (cluster dkms1, eu-north-1)

Bugs conocidos / mitigaciones documentadas en
`.claude/projects/-home-pablopio-Documentos-trabajo-atlantic-dkms-rust/memory/`:

- **Bug R-002** `kme.local_qkc_id NotNull`: mitigado pasando
  `--node-id-offset` que no colisione con sims previas.
- **Bug loadtest-403**: mitigado autenticando como `config_user`
  (uid=3 confirmado).
- **Bug ck_host_ipv4**: cota dura `node_id ≤ 155`.
- Pattern de port-forward: `kubectl -n dkms-main-ns port-forward
  svc/authz 18081:8081` y `svc/orchestator 18080:8080`.
- Para sims de saturación: `POST /orch/web/simulations/<id>/tests` —
  builtin loadtest deployment `dkms-loadtest:v1`.

### Sobre el run baseline existente

- Carpeta: `tests/results/20260518T160920Z-random-n20-d3.0-srnd/`
- Métricas: 2359 SAE requests, 100% OK; 48/380 commodities saturados;
  ratio mediana observed/theoretical = 0.585.
- Servirá como números de partida para OBJ-005 al ejecutar
  `bench_multipath.py`.

### Sobre las 3 topologías de robustez

1. **Pequeña densa** — pocas (4-6) DKMSs, alta conectividad. Test de
   regresión: el multipath no debe degradar respecto a single-path
   cuando solo hay un camino útil.
2. **Mediana operador** — ~N=20, density ≈ 3.0. Caso realista,
   matches el baseline ya existente.
3. **Cuello obvio** (`bridge` builder, OBJ-004) — dos clusters mesh
   conectados por un único edge. Caso patológico que single-path no
   sabe gestionar; multipath debería balancear el cuello.

### Sobre los 6 criterios de aceptación

A definir formalmente en `project_multipath_design.md` (OBJ-001). El
agente debe usar `bench_multipath.py` (OBJ-005) para medirlos. Los
6 criterios son la **definición externa de "el cambio funciona"**.
Mientras no estén definidos, el agente NO puede declarar completado
en .results.md.

## Iter 005 (2026-05-18)

**Objetivos:** OBJ-007 + OBJ-008 + OBJ-009 (juntos por interdependencia lógica).

**Trabajo principal — solver K-Splittable MCF operativo:**
- `McfSnapshot.rates_per_path: HashMap<String, Vec<f64>>` (campo nuevo). `merge_into` lo propaga.
- `build_commodities` aplica `filter_overlapping_paths(raw_paths, 0.70)` tras Yen's.
- `weighted_maxmin` itera sobre pseudo-flujos `(commodity_idx, path_idx)`. Pesos heredados del commodity. Saturación de edge congela todos los pseudo-flujos que lo cruzan.
- `subtract_usage` itera todos los paths con rate > 0 y resta capacidad por path.
- Forwarding output: por cada path con rate > 0, en cada hop entry con `omega_p = rate_p / total`. Múltiples paths con (u, nxt) común acumulan sus omegas.

**Verificación:**
- `cargo build -p sdn --release` → OK.
- `cargo test -p sdn --lib --release` → **67 passed** (era 61 + 6 nuevos multipath).
- `cargo clippy -p sdn --release -- -D warnings` → OK.

**Tests añadidos (6):**
1. multipath_one_commodity_two_disjoint_paths_balanced — split equitativo en triángulo simétrico, suma omegas QKC origen = 1.0.
2. multipath_single_useful_path_degrades_to_single_path — topología lineal, comportamiento single-path.
3. multipath_two_commodities_sharing_bridge_balance_via_alternate — multi-flow, sum omega invariante en cada QKC origen.
4. multipath_omega_entries_at_origin_sum_to_one — invariante OBJ-009.
5. multipath_rates_per_path_consistent_with_total — Σ rpp = rates[fid].
6. subtract_usage_respects_capacity_invariant — ningún edge sobrecargado.

**Decisiones:**
- Filter en `build_commodities`, no dentro de `weighted_maxmin`. Más limpio.
- `rates_per_path` como campo nuevo (no extender forwarding). Necesario para `subtract_usage` y RPC futuro.
- `rates` y `rates_by_dkms` siguen siendo totales agregados — API DKMS cliente no cambia.

**Hallazgos:**
- **Caso simétrico (triángulo, ambas direcciones) NO mejora throughput por commodity** — el water-filling reparte la capacidad limitada por igual. Lo que sí cambia es que ambos paths se usan. La mejora real se verá en topologías asimétricas/random/bridge.
- `merge_into` debe propagar `rates_per_path` para que HIGH y LOW tier no se pisen.
- Coste solver: O(P × E²) con P = Σ_c |c.paths|. Con K=3 y N=20, P ≤ 1140, E=30 → ~1M ops/solve. En release <50 ms estimado.
- El forwarding actual publicado al QKC sigue siendo destination-based; el ORR consumirá las ratios via OBJ-010 (RPC nuevo).
