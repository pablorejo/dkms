- [ ] OBJ-024: **Auto-fix operacional** (ver R-018). El agente intenta diagnosticar y corregir errores **OPERACIONALES** del deploy (NO algorítmicos — esos están bloqueados por R-016). Casos cubiertos y orden de acción:
  1. **Pod en CrashLoopBackOff por error de configuración** (env var faltante, mala URL, etc.): corregir el env var en el deployment y rollout restart.
  2. **Pod en CrashLoopBackOff por panic Rust al arrancar**: leer logs (`kubectl logs <pod> --previous`), identificar la línea, hacer fix mínimo en el código si es claro (un `unwrap` mal, un campo opcional no manejado). Rebuild + push (volver a R-014 gate) + redeploy. Documentar el fix.
  3. **OOMKilled**: subir `resources.limits.memory` del deployment afectado en 50 %. Rollout restart.
  4. **Bootstrap race ORR↔ORR** (ver memory previo del proyecto): hacer stop+rerun de la sim de validación afectada, NO `rollout restart` aislado.
  5. **Ingress / mTLS errors**: verificar que `ingress-proxy-tls` secret existe en el namespace; regenerar via orchestator CA si falta.
  6. **K8s scheduling failures (Insufficient CPU/memory)**: esperar autoscale del cluster (HPA / cluster autoscaler), max 5 min. Si tras 5 min sigue Pending, PARAR y reportar (no auto-resize de cluster).

  Si **ningún caso aplica** o el fix intentado **no resuelve tras 2 retries** → PARAR con `Estado: BLOQUEADO_AUTO_FIX_FALLO` y reportar al usuario con stack trace + logs relevantes. NO seguir intentando arreglos a ciegas.

  Cada acción correctiva se documenta en `iter_NNN/notes.md` con: síntoma observado, hipótesis, fix aplicado, verificación post-fix.
