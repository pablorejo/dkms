# Arquitectura del agente multipath-opt2-deploy

## Vision general

Cerrar la migracion K-Splittable Multi-Commodity Flow (MCF) que el agente previo `agent-multipath-sdn/` dejo en codigo Fases A/B/C en `main` (commits `f8d54af`, `b5ce2e3`, `509fae5`) sin cablear el path completo. Este agente:

1. Cabla el flujo end-to-end: ORR origen elige path via `pick_multipath_qkc_hops` y lo escribe en `Frame.header_qkc_mp`; cada QKC en la ruta pop-ea el siguiente hop del path y reenvia; ORR destino recibe normalmente.
2. Construye y publica imagenes Docker nuevas (sdn:v8, orr:v3, qkc:v3) con el wiring activo.
3. Despliega en EKS dkms1 (eu-north-1) reconfigurando el orchestator para usar las nuevas imagenes.
4. Mide post-cambio en 3 topologias (mesh 3x3, random n=20 d=3, bridge 2x4) y compara contra los baselines del agente previo.
5. Reporta y cierra (o bloquea si no cumple criterios).

## Flujos de datos / control

### Inicializacion (ya funciona, no se toca)
```
SDN startup -> carga topology desde JSON -> solver MCF -> publica via stream_topology
ORR startup -> conecta SDN -> recibe topology -> bootstrap ML-KEM con peers ORR
ORR (durante operacion) -> peticion GetPathsWithRatios al SDN -> rellena paths_cache_multipath con AliasSampler
```

### Envio de mensaje origen->destino (NUEVO con wiring de este agente)
```
DKMS-origen -> ORR-origen::send_message(dest_orr, payload)
  ORR-origen:
    if MULTIPATH_ENABLED:
      path = pick_multipath_qkc_hops(src_dkms, dst_dkms)
      if path.is_some():
        frame.header_qkc_mp = wire::encode_qkc_path(&path)
    enviar frame al QKC-local via TCP binario
  QKC-1 (QKC-local del ORR-origen)::handle_local_send(frame):
    if !frame.header_qkc_mp.is_empty():
      (next_hop, rest) = wire::pop_qkc_path_next_hop(frame.header_qkc_mp)
      frame.header_qkc_mp = rest
      next_destination = next_hop
    else:
      next_destination = routing_table[frame.dest_final]
    enviar frame a QKC[next_destination]
  QKC-2..N (intermedios)::handle_incoming(frame):
    (mismo patron: pop path si existe, else fallback routing table)
  QKC-N (QKC-local del ORR-destino)::handle_incoming(frame):
    path queda vacio en este punto -> entregar al ORR-destino local
  ORR-destino::handle_incoming -> entrega a DKMS-destino
```

## Decisiones de diseno

- **Opcion 2 - Source routing en `Frame.header_qkc_mp`** elegida sobre alternativas porque:
  - QKC se mantiene STATELESS por flow. No tabla `flow_id -> path` (que requeriria invalidation, sincronizacion entre QKCs, manejo de timeouts).
  - Wire-compatible: el campo `header_qkc_mp` YA existe como `Vec<u8>` opcional, reservado para metadatos del QKC. Esto era exactamente su proposito.
  - Cada paquete puede llevar un path distinto -> es lo que multipath necesita (sampler O(1) por paquete).
  - Backwards-compatible: QKC viejo que recibe `header_qkc_mp` vacio se comporta igual que siempre (fallback routing table). QKC nuevo con `MULTIPATH_ENABLED=false` en ORR origen tampoco recibe path -> fallback. Cuando MULTIPATH_ENABLED=true y el origen escribe path: QKC nuevo lo respeta; QKC viejo lo IGNORA (no entiende el contenido del campo) y cae a routing table -> degradacion a single-path silenciosa, no crash. Para que multipath funcione, necesitas la version nueva del QKC en TODOS los hops del path; si falta en alguno, ese hop hace single-path y el siguiente potencialmente diverge. Por eso el deploy en Fase E es completo (todos los QKC del cluster).

- **Opt-in via env var `MULTIPATH_ENABLED=true`** en ORR origen: el control de activacion vive en el ORR origen, no en el QKC. Si el flag esta OFF: no se escribe path en `header_qkc_mp`, los QKC ven el campo vacio y hacen routing table normal. Ventaja: rollback parcial trivial (basta con poner el flag a false en una sim concreta sin redeploy).

- **Formato msgpack `{"qkc_path": [u32, u32, ...]}`** (no JSON, no protobuf): msgpack es binario compacto, `rmp_serde` ya esta en el workspace, permite extension (anadir keys futuras como `qos_class`, `trace_id` sin breaking change), y el decode tolera bytes vacios (devuelve estructura vacia o Err controlable). Los `u32` mapean a `qkc_id` numericos como los devuelve `GetPathsWithRatios::qkc_hops`.

- **`pop_qkc_path_next_hop` consume el primer elemento Y devuelve los bytes re-encodeados**: hace el coste explicito (decode + slice + re-encode por hop). Para topologias <10 hops el msgpack es <100 B, el overhead es marginal frente al cifrado ML-KEM. Si se vuelve cuello, optimizacion futura: usar Vec en sitio + serializar al final, o cambiar a un formato cabecera-fija sin msgpack.

- **OBJ-004: `src_dkms`/`dst_dkms` lookup**: pendiente decidir entre (a) caller pasa o (b) ORR lookup local. La decision se documentara en la iter que toque OBJ-004 con tradeoffs concretos. Sesgo inicial: (b) si la topology del ORR ya tiene el mapping orr_id->dkms_id (probable, dado que el agente previo cableo cache); (a) solo si requiere cambios disruptivos en ORR.

## Restricciones arquitectonicas

Coherentes con `.restrict.md`:

1. Wire binary format (`Frame` layout en `wire/src/lib.rs`) NO cambia. Solo se anaden helpers que producen/consumen contenido del campo `header_qkc_mp` ya existente.
2. QKC sigue STATELESS por flow. NO tablas `flow_id -> path` ni cache de paths.
3. QKC NO expone HTTP. NO RPC adicionales. Solo lee el campo opcional del wire que ya existia.
4. SDN solver max-min HIGH/LOW se mantiene. Multipath actua sobre pseudo-flujos ya implementados por el agente previo; este agente NO modifica la formula.
5. DKMS NO se modifica salvo decision OBJ-004 obligue (caso (a)). En caso (a), cambio MINIMO y solo el call site.
6. Multipath OPT-IN via `MULTIPATH_ENABLED=true`. Default OFF. Permite rollback parcial sin redeploy de imagenes.
7. Imagenes nuevas (`sdn:v8`, `orr:v3`, `qkc:v3`) coexisten con previas (`:v7`, `:v2`, `:vX`). Rollback = re-set env vars + rollout.
